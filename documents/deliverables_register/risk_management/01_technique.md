# Risques techniques

8 risques. Score = probabilité × impact. Voir [README.md](README.md) pour la méthode et la synthèse.

| ID    | Titre                                                 | Description                                                                                                                       | Probabilité | Impact | Score  | Plan d’action                                                                                                                                        |
| ----- | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | :---------: | :----: | :----: | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| RT-01 | **Mauvais dimensionnement de l’infrastructure**       | Sous-dimensionnement : latence, erreurs, service instable. Sur-dimensionnement : coût inutile.                                    |      3      |   4    | **12** | Mettre en place du monitoring CPU/RAM/DB/API, faire des tests de charge, prévoir un scaling progressif, définir des seuils d’alerte.                 |
| RT-02 | **Point unique de panne**                             | Un seul serveur, une seule base de données ou un seul service critique peut rendre toute l’application indisponible.              |      3      |   5    | **15** | Prévoir sauvegarde serveur, sauvegarde DB, hébergement cloud fiable, procédure de redémarrage.                                                       |
| RT-03 | **Perte ou corruption de base de données**            | Bug, suppression accidentelle, migration ratée ou corruption sans sauvegarde exploitable.                                         |      2      |   5    | **10** | Sauvegardes automatiques, tests de restauration, versionner la DB, limiter les accès en écriture.                                                    |
| RT-04 | **Dépendance à un service externe**                   | SMS, SMTP, stockage S3, paiement ou API externe indisponible.                                                                     |      3      |   4    | **12** | Prévoir un fournisseur alternatif, gérer les erreurs proprement, mettre une file d’attente pour réessayer, afficher un message utilisateur clair.    |
| RT-05 | **Mauvaise qualité du code**                          | Code difficile à maintenir, bugs fréquents, régressions après modification.                                                       |      3      |   4    | **12** | Revue de code, tests automatisés, conventions de développement, documentation technique minimale.                                                    |
| RT-06 | **Mauvaise gestion des performances**                 | Pages lentes, requêtes DB non optimisées, images trop lourdes.                                                                    |      3      |   4    | **12** | Optimiser les requêtes, compresser les images, utiliser du cache, surveiller les temps de réponse.                                                   |
| RT-07 | **Dépendance à un fournisseur cloud unique**          | Tout repose sur Azure : hausse de prix, changement d'offre ou coupure fournisseur impactent tout, et migrer ailleurs est coûteux. |      3      |   3    | **9**  | Garder les services conteneurisés et l'infra en Terraform pour rester portable, éviter les services trop propriétaires, documenter la réversibilité. |
| RT-08 | **Panne régionale / absence de plan de reprise (DR)** | L'infra est sur une seule région (France Central) ; une panne régionale rend tout indisponible, sans procédure de bascule.        |      2      |   5    | **10** | Définir RTO/RPO, sauvegardes répliquées hors région (Atlas + Blob), documenter et tester une procédure de restauration.                              |
